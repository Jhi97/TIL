### 인덱스

> 대용량 테이블에서 필요한 데이터만 빠르게 효율적으로 액세스하기위해 사용하는 오브젝트

- DBMS는 일반적으로 B\*Tree 인덱스를 사용함

### 인덱스 수직적 탐색 / 수평적 탐색

- 수직적 탐색
  > 정렬된 인덱스 레코드 중 조건을 만족하는 첫 번째 레코드를 찾는 과정
  > 즉, `인덱스 스캔 시작지점을 찾는 과정`
- 수평적 탐색
  > 찾고자 하는 데이터가 더 안나타날 때 까지 인덱스 리프 블록을 수평적으로 스캔
  > `인덱스에서 본격적으로 데이터를 찾는 과정`

### 인덱스를 Range Scan 할 수 없는 이유

> 인덱스 컬럼을 가공하면 인덱스를 정상적으로 사용(Range Scan)할 수 없다.

쿼리 조건 내 인덱스 컬럼을 가공했을때 사용할 수 없는 이유는 `인덱스 스캔 시작/종료점`을 찾을 수 없기 때문이다.

```sql
-- 가능한 경우 (시작, 종료지점을 알 수 있음)
WHERE 생년월일 BETWEEN '20260101' AND '20260201'

-- 인덱스 사용 불가한 경우 (시작, 종료지점을 알 수 없음)
WHERE SUBSTR(생년월일, 5, 2) = '05'

WHERE NVL(주문수량, 0) < 100

WHERE 업체명 LIKE '%두잇%'

/*UNION ALL 등으로 변환하면 인덱스 사용 가능 (OR Expansion)*/
WHERE (전화번호 = :tel_no OR 고객명 = :cust_nm)
WHERE 전화번호 IN ('01000001111', '01000002222')
```

이때, IN 조건절에 대해서는 SQL 옵티마이저가 IN-List Iterator 방식 사용

→ IN-List 개수만큼 Index Range Scan을 반복하는 것

### 인덱스를 이용한 소트 연산 생략

인덱스를 Range Scan 할 수 있는 이유는 **데이터가 정렬**되어있기 때문이다.

```sql
CREATE INDEX N1_ITEM ON 상태변경이력 (장비번호, 변경일자, 변경순번);

SELECT *
FROM 상태변경이력
WHERE 장비번호 = 'C'
AND 변경일자 = '20260101'
;
```

위와 같을때, 옵티마이저는 ORDER BY가 있어도 정렬연산을 따로 수행하지 않는다.

-소트머지 연산 생략 불가 케이스

```sql
SELECT *
FROM 상태변경이력
WHERE 장비번호 = 'C'
ORDER BY 변경일자 || 변경순번

SELECT *
FROM (
  SELECT TO_CHAR(A.주문번호, 'FM000000') AS 주문번호, A.업체번호, A.주문금액
  FROM 주문 A
  WHERE A.주문일자 = :dt
  AND A.주문번호 > NVL(:next_ord_no, 0)
  ORDER BY 주문번호 -- 여기서 주문번호가 TO_CHAR문으로 적용됨, alias 붙여서 A.주문번호로 기입해야 함
)
WHERE ROWNUM <= 30
```
